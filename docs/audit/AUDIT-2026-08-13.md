# Security & correctness audit — 2026-08-13

**Audited at:** `643aa90` (`dev`, 0.48.0-dev.38) · **Fixes shipped on:** `dev`, 0.48.0-dev.39 · **Baseline before
changes:** lint clean, 798 server + 123 web tests green from a clean `npm ci` on Ubuntu 26.04 / Node 22.

A full read of the server's security-relevant surface and the money path, plus the newest 0.48.0 code (refunds,
saved-method ordering, the PWA routes, past due), followed by fixes for everything found. Second audit of this
app; the first was [2026-08-04](./SECURITY_AUDIT.md), and two of its open items are closed here.

**Method.** Read, then probe, then fix, then prove. Every finding below was either confirmed by running it —
a throwaway test file against a real migrated database, its output quoted where it matters — or is a
documented invariant compared against the code that implements it. Nothing here is "this looks wrong": two
things that looked wrong turned out to be fine and are recorded as such at the bottom, because a review that
only lists problems tells you nothing about the rest. Every fix ships with a test that fails without it.

### OMS-023 — a distributed password spray on one account was unthrottled {#oms-023}

**Severity: Medium.** `CLAUDE.md` §14 has always required internet-facing rate limits "per-IP **and**
per-account". Only per-IP existed (8 failures / 15 minutes, keyed on the real client IP). Finance and parent
logins are reachable over the Cloudflare tunnel, a parent's username **is** their email address, and a
hundred hosts making eight attempts each never trips a per-IP counter.

The 2026-08-04 audit raised this as [OMS-010] and deliberately did not fix it, because the obvious fix has a
real downside: a per-account lockout is a denial-of-service primitive against a named person. It offered four
options and recommended (b) — alert, don't lock.

**Shipped: both, and the trade-off is stated in the code rather than left implicit.**

- `loginAccountLimiter` (`security/rateLimit.ts`) caps failures per **account name**, deliberately looser than
  the per-IP bucket because its key is attacker-chosen: **25 failures in 15 minutes, blocked for 15**. That is
  far past honest mistyping and far short of what guessing a password needs.
- On the **transition** into blocked, and only when the name is a real account, `alertStaff('login-blocked')`
  emails whoever the office listed — the recommendation from last time. Once per name per window, never per
  attempt, and nothing at all for invented usernames, so it cannot be turned into a mail flood.

**Why the DoS objection is answered rather than dismissed:** 25 attempts to lock, 15 minutes to expire, a
parent can still reset by email, an admin can reset a staff password, and admin sign-in is LAN-only — locking
an admin means already being on the masjid's Wi-Fi. Against that: without the cap, the whole internet had
unlimited attempts on a known finance address, forever.

**Not an enumeration oracle:** the bucket counts failures on the *supplied* name whether or not the account
exists, so a lockout says nothing about which names are real. The alert is what distinguishes them, and it
goes to the office, not the caller.

**One thing to know about the alert in the field:** `defaultOn` applies to a **newly added** recipient. An
install that already has addresses in Settings → Email alerts gets a new **Sign-in blocked** column, unticked,
because silently changing what somebody already receives is its own kind of wrong. Same as `past-due` and
`payment-refunded` earlier in 0.48.0. The cap itself needs no configuration and is on everywhere.

**Tests:** `test/loginSpray.test.ts` — 25 attempts from 25 different addresses then a 26th from a fresh one;
the lock follows the name and not the machine (an untouched account still signs in from an address that was
just spraying); an unknown name locks identically; a real sign-in clears the counter; the per-IP limiter still
bites at eight; and the alert fires exactly once for a real account and never for an invented one.

### OMS-024 — two places disagreed about what a username is {#oms-024}

**Severity: Medium** (account integrity; no privilege escalation).

Signing in has always looked an account up **case-insensitively**, for a good reason: a parent's username is
their email address and a phone keyboard capitalises the first letter. But every check asking "is this
username taken?" compared **exactly** — `staff.create`, `mintInvite`, and both halves of `inviteAccept` — and
`users.username` is UNIQUE under SQLite's binary collation. So `Office` and `office` were two accounts.

**Confirmed by probe, not by reading.** Creating `Office` (finance) then `office` (admin) was accepted, and
then signing in as `office` with the *second* account's password authenticated as the **first** one's role:

```
PROBE-2 second account with a case variant -> ACCEPTED
PROBE-2 users: [{"u":"Office","r":"finance"},{"u":"office","r":"admin"}]
PROBE-2 login with the first row password -> signed in as role=finance
```

The admin account an office had just created could never be signed into, with no error anywhere to say so.
No escalation — the password is verified against whichever row was selected — but a silently broken account,
and the same shape reachable through a guardian invite whose email matched a staff login in another case.

**Fixed** by making one place own the rule: `auth/usernames.ts`. `usernameTaken()` compares case-insensitively
and is used by every creation door; `findUserByUsername()` is the single lookup, and it tries an **exact match
first**, then the loose one — which is what looks after an install that already made such a pair before the
fix (each person reaches their own account by typing their own name). The stored value keeps the case an admin
typed, because that is what the staff screen shows back.

**Tests:** `test/usernameCase.test.ts` — creation refused in three casings and through the invite door;
a genuinely different name still allowed; the typed case preserved; loose lookup still works; and the
exact-match-first behaviour pinned for the legacy pair.

### OMS-025 — unvalidated dates on the money path {#oms-025}

**Severity: Medium.** Three inputs in the billing router took `z.string().max(20)` and were never checked:
`recordManualPayment.occurredAt`, the `dueDate` on both invoice-generation procedures, and the mid-year
go-live's `asOf`. §9 fixes the storage format as ISO precisely because **every date column is compared as
text**, and that rule was documented but unenforced at the boundary that writes it.

Two different failures, and both were reachable:

1. **A payment date reached the office as a database error.** `new Date('T12:00:00')` is `NaN`, SQLite stores
   that as NULL, and the NOT NULL column refuses. Probed:

   ```
   PROBE occurredAt="" -> TRPCError code=INTERNAL_SERVER_ERROR :: NOT NULL constraint failed: payments.occurred_at
   ```

   **Clearing the date box in the record-a-payment form was enough to do it** — the submit button did not
   require the date, only the child and the amount. Nothing was written (0 rows), so no corruption; but §18
   says no raw error reaches the user, and this one is what a volunteer would have seen at the desk.

2. **A due date would have been stored happily and then quietly misbehaved for good.** `invoices.due_date` is
   TEXT, so `dueDate: 'lol'` persists, sorts wherever it likes, is never past due (`due_date < today` is
   false), and is invisible to autopay (`due_date <= today` is false too). A bill that can never be collected
   and never chased, with no error anywhere.

**Fixed** with `isIsoDay()` in `settings/dates.ts` — the module that already owns every other date edge —
plus a friendly refusal in the router. A regex would not have been enough: `2026-13-45` is ten characters of
the right shape and is not a day, so the check asks `parseDateInput` (which already rejects 31 February by
comparing back) and requires the value to round-trip unchanged. The mid-year date is checked **once, before a
single artifact is written**, because it lands on every carry-in row the run creates. Both payment forms now
also require the date client-side, so the friendly path is a disabled button rather than an error.

**Tests:** `test/moneyDates.test.ts` — `isIsoDay` against real days, right-shape non-days and other notations;
each of the three inputs refused with `BAD_REQUEST` and nothing written; the field named in the message; an
empty due date still meaning "the first of that month"; real dates still accepted.

### OMS-026 — a card payment relabelled as one to hand back {#oms-026}

**Severity: Medium** (money advice, not access).

`refundableTransactions` computed each row's route as `pi && stripeReady() ? 'stripe' : 'manual'`. Stripe keys
are fetched from the platform (§13.1) and cleared on any reload failure, so **a minute of the platform being
unreachable relabelled every card payment `manual`** — and `manual` is the row whose copy tells the office
"the money still has to be handed back", both in the list and in the confirmation dialog. An office that
followed it would hand over cash; Stripe reconnects; the card is refunded too. The family is paid twice.

**Fixed** by separating two facts that are not the same: `route` describes how the money **arrived** and never
changes (`pi ? 'stripe' : 'manual'`), while `billing.refundable` now reports `cardRefundsReady` alongside it.
The refund screen disables the button on a card row when card refunds are unavailable and says why, instead of
offering an action that will be refused. The engine already refused correctly — it checks the PaymentIntent,
not the route — which is why this was misleading rather than dangerous on its own.

**Test:** `test/refunds.test.ts` — with the Stripe client dropped, the row is still `route: 'stripe'` and
`cardRefundsReady` is `false`.

### OMS-028 — the SPA shell had no `nosniff` and no `Referrer-Policy` {#oms-028}

**Severity: Low.** The shell was sent with `cache-control: no-store` and nothing else. The invite, reset and
register pages carry a **single-use token in the query string**, and the portal's pay page loads Stripe's
script from another origin. Modern browsers default to `strict-origin-when-cross-origin`, which strips the
path — but that is a default, not a promise, and an older webview (which is what a parent's phone may be) can
still send the full URL on a same-protocol cross-origin request. A token in someone else's logs cannot be
un-leaked.

**Fixed:** `x-content-type-options: nosniff` and `referrer-policy: no-referrer` on the shell, both entry
points (the printable documents have had these plus a CSP since the last audit).

**Deliberately not added:** `X-Frame-Options` / `frame-ancestors`. Whether OpenMasjidOS embeds an app in its
dashboard is the platform's business, and guessing wrong breaks the entire UI rather than one page. See
[still open](#still-open) for the CSP question.

### OMS-027 — `LIKE` with a wildcard-bearing key {#oms-027}

**Severity: Info** — no live bug, fixed for robustness.

`payments/refunds.ts` gathered a transaction's sibling rows with `like(idempotencyKey, `${key}:%`)`. `_` is a
LIKE wildcard and Stripe PaymentIntent ids are full of them (`pi_3Pabc…`), so the pattern is looser than it
reads. Two other places in this codebase — `ledger.recordedSplit` and the Fabric `check` method — use `substr`
instead and each carries a comment explaining exactly this. Here the following `externalRef` filter caught
anything a loose match let through, so nothing was wrong in practice.

**Fixed** to the same `substr` comparison, because a query that is only correct because of a later filter is
one refactor away from being wrong, and this is the refund path.

### OMS-017 — documentation that described a system that does not exist {#oms-017}

**Severity: Info, and it misleads contributors.** Raised by the last audit and left open as "authoring a
specification, which is yours". `CLAUDE.md` declares itself the single source of truth and carried a banner
admitting that several sections no longer applied — a banner is not documentation.

**Rewritten against the code at 0.48.0.** §4 (scope), §5 (the permission matrix — three roles, not five, and
the capabilities that exist), §6 (the architecture diagram), §7 (the stack, minus the PDF renderer and
nodemailer), §8 (the real file tree), §9 (the real table list, plus the new invariants), §10 (the real
manifest keys), §13.4 (**there is no webhook** — replaced with the four pull paths and why), §17, §18 and §20.
§11's wire contract, §12.4's origin policy and §19's release runbook were already accurate and are unchanged
in substance. Section **numbers** never move: hundreds of code comments cite them.

`docs/PAYMENTS.md` was a stub still describing webhook signature verification and endpoint auto-registration;
it is now a real document, leading with the no-webhook table. `CONTRIBUTING.md` gained the things a new
contributor actually needs — how to run it, that Linux is where tests are run, the house rules that come up
in review, a map of where things live, and how to report a vulnerability privately.

## Verified sound

Read carefully and found correct. Recorded because the next auditor should not have to re-derive it, and
because "no findings here" is itself a result.

- **Origin classification** (`security/origin.ts`) — grants `lan` only on a positive signal (a private
  effective client IP), trusts forwarding headers only when the TCP peer is local, and fails toward `tunnel`,
  which only ever removes privileges. Sound, and better than the spec §12.4 originally described.
- **The Fabric provider** — tunnel-origin 404 before anything else, constant-time secret compare, zod before
  logic, uniform `found:false` on every mismatch flavour, per-code lockout shared with self-registration,
  never a full surname. The v1/v2 request tolerance is deliberate and documented.
- **Parent scoping** — every portal procedure resolves the caller's households through `guardian_users` and
  filters in SQL; `assertFamilyAccess` on every mutation that names a family; `confirmPayment` additionally
  verifies the PaymentIntent's own metadata names that household.
- **The ledger** — derived balances, immutable payments, per-line allocation, a stored payer instruction
  re-honoured on every recompute, idempotency at the DB with the correct `substr` prefix match, and the
  `recordedSplit`-before-deriving rule that keeps a replay from double-recording a split charge.
- **CSV export** — formula-injection prefixing (`=`,`+`,`-`,`@`,tab,CR) *before* quoting, on every cell, with
  the two problems (quoting vs. injection) correctly kept separate.
- **The printed documents** — every interpolated value escaped; the accent colour re-validated against a hex
  pattern **on read** and the logo re-validated by magic bytes, because both land inside a `<style>` block and
  an `<img>` on a rendered page; `no-store` + CSP + `nosniff` + `no-referrer`; role and origin re-checked per
  request; a school restriction that cannot be widened by editing the URL.
- **Secrets** — Stripe secret key in memory only and cleared on any reload failure; session, invite and reset
  tokens stored only as SHA-256; no mail credentials anywhere; `OPENMASJID_APP_SECRET` never persisted.
- **Logs** — ids, codes and counts only, at every call site I read, including the failure paths.
- **Alerts** — the two-text discipline holds everywhere (`text` may name a household, `publicText` never
  does), and the manifest-vs-code guard plus the new i18n-label guard mean neither half can rot silently.
- **`inArray` with an empty array** — checked against the installed drizzle (0.38.3), which emits `false`
  rather than invalid SQL, so the several call sites that can pass an empty list are safe.
- **The snapshot** — `VACUUM INTO` a temp path, `integrity_check` it, then rename over the live file, so a tar
  of a running volume always contains one restorable copy.

Two things that looked like bugs and were not: the empty-array `inArray` calls above, and the mid-year
`asOf: ''` path (`carryIn` treats an empty string as "today" before it ever reaches a `Date`).

## Still open {#still-open}

Nothing new that needs a decision; these carry forward from the last audit and are unchanged.

- **[OMS-021] Timezone is UTC everywhere.** Still true, still not a money bug (it is internally consistent),
  still means a payment recorded in the evening west of UTC prints the next day. The fix has to move
  rendering, `todayIso()` and period derivation together — see `ACTION_REQUIRED.md` §5.3.
- **[OMS-018] HTTP-layer test coverage is thin.** The harness builds tRPC callers and never boots Fastify, so
  the SPA fallback, base-path stripping, `/api/logo`, `/manifest.webmanifest` and `/sw.js` have no HTTP-level
  test. `statementRoute.test.ts` and `spaCache.test.ts` are the only ones. This audit's fixes are all at the
  router or module level and are covered; the gap is unchanged.
- **A CSP for the SPA shell.** Worth doing and deliberately not attempted here: the parent portal loads
  `js.stripe.com` and frames Stripe's own iframes, so a policy that is wrong breaks payments rather than
  degrading. It wants a real browser and a Stripe test-mode run, not a careful guess.
- **`stripe_events` is vestigial.** It deduped webhook deliveries; there is no webhook (§13.4). Nothing reads
  it. Left in place rather than dropped — a migration to remove an unused empty table is churn on the money
  schema for no gain — and now recorded in §9 so nobody builds on it.
- **Deleting a household's last child leaves the household row behind.** `studentDelete` removes the student
  (only ever one who was never billed) but not the now-empty `families` row, which then shows up in the
  balances CSV as a name with `0.00` against it. Cosmetic, and *not* fixed on purpose: deleting a household as
  a side effect of deleting a child is a behaviour change, and the honest version of it is a decision about
  what the office expects to happen, not a tidy-up.
